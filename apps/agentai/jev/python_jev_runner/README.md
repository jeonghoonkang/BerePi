# Python Jev Runner 대화형 응용 서비스 설계

작성일: 2026-10-28

상태: 구현을 위한 설계 문서. 이 디렉터리의 Runner 실행 프로그램은 아직 구현하지 않았다.

## 1. 목적과 사용자 경험

Python Jev Runner는 사용자가 응용 프로그램의 명령어나 함수 이름을 외우지 않고,
말풍선 형태의 대화로 기능을 알아보고 필요한 값을 전달하여 실행하는 데스크톱 프로그램이다.
실행 대상은 Python JEV Creator가 생성한 프로젝트 또는 Runner 실행 규약을 갖춘 Python 프로젝트다.

창을 실행하면 첫 말풍선에 다음 문구를 그대로 출력한다.

> 저는 jev 코드를 실행하는 runner 입니다

사용자는 프로젝트를 선택한 뒤 “너는 어떤 기능을 제공해?”라고 질문할 수 있다.
Runner는 선택한 응용 서비스가 등록한 기능을 설명하고, 후속 질문의 문맥을 유지하며
실행에 필요한 경로 등의 값을 차례로 받는다. 기능 설명은 실제 등록된 기능과 일치해야 한다.

### 대표 대화

사진 서비스가 로드되어 있고 복사 위치와 DB 설정이 준비된 경우의 예다.
아래 경로와 처리 건수는 설계 예시다.

| 발화자 | 화면에 표시할 내용 | 내부 처리 |
| --- | --- | --- |
| Runner | 저는 jev 코드를 실행하는 runner 입니다 | 최초 안내 |
| 사용자 | 너는 어떤 기능을 제공해? | 기능 안내 의도 선택 |
| Runner | 저는 사진을 복사하고, 사진의 메타데이터를 저장합니다. | 서비스 명세에서 기능 설명 |
| 사용자 | 제가 그러면 처리할 사진 경로를 알려주면 돼? | 직전 기능에 대한 입력 방법 질문 |
| Runner | 네. 경로 알려주면, 사진을 복사하고 DB로 해당 metadata 를 저장하겠습니다. | 필요한 입력 안내, 아직 실행하지 않음 |
| 사용자 | E:\photos\여행 | 현재 작업의 원본 경로로 저장 |
| Runner | 여행 폴더의 사진을 E:\photo_archive에 복사하고, 설정된 DB에 메타데이터를 저장할 수 있습니다. 실행하려면 ‘실행해 줘’라고 입력해 주세요. | 대상 확인 및 실행 가능한 계획 표시 |
| 사용자 | 실행해 줘 | 현재 계획으로 작업 시작 |
| Runner | 사진 처리 중입니다. 12개 중 5개 완료했습니다. | 작업 이벤트 표시 |
| Runner | 사진 12개를 복사하고 메타데이터 12건을 저장했습니다. | 실제 실행 결과 요약 |

사용자가 처음부터 “E:\photos\여행 사진을 복사하고 메타데이터를 저장해 줘”라고
명확하게 실행을 요청했고 나머지 값이 준비되어 있으면, 계획을 표시하고 바로 실행한다.
이미 요청한 실행에 같은 확인을 반복하지 않는다. 입력 방법을 물은 것인지 실행을
지시한 것인지 구분하고, 경로만 전달한 경우에는 앞선 대화에서 실행 요청이 있었는지 확인한다.

복사 위치나 DB가 준비되지 않았다면 처리 가능하다고 단정하지 않고, 필요한 설정을
추가로 안내한다. DB 비밀번호는 일반 채팅 대신 별도 설정에서 입력한다.

## 2. Jev와 대화 처리의 역할

TypeSafe 공식 문서에 따르면 Jev는 상태와 타입이 지정된 질문을 받아 구조화된
판단을 반환한다. 임의의 설명 문장이나 Python 코드를 생성하는 용도로 쓰지 않는다.
[공식 모델 설명](https://docs.typesafe.ai/introduction)

이 설계의 기본안은 **Jev 의도 선택 + 대화 상태 관리 + 명세 기반 한국어 응답**이다.
별도 생성형 LLM 없이 위 대표 대화를 지원한다. 사용자에게는 응용 서비스가
대답하는 것으로 보이지만, 실제 문장은 Runner가 등록된 설명과 실행 결과로 구성한다.
자유로운 장문 대화가 필요할 때만 생성형 LLM 응답기를 선택적으로 확장한다.

| 구성 요소 | 담당 역할 |
| --- | --- |
| Jev | 기능 안내, 입력 방법 질문, 기능 선택, 실행 요청 등의 의미 분류 |
| 대화 관리자 | 현재 서비스·기능·입력값·실행 계획을 기억하고 다음 단계 결정 |
| 응답 렌더러 | 등록된 기능 설명, 부족한 입력, 진행 상태, 실제 결과를 말풍선 문장으로 표현 |
| 실행 관리자 | 검증한 인자를 등록된 응용 어댑터에 전달하고 결과 수집 |
| Jev 응용 코드 | 실제 사진 복사, DB 저장 등 업무 수행. Creator가 삽입한 내부 Jev 조건도 이 단계에서 실행 |

Runner의 기능 선택용 Jev와 응용 코드 내부의 Jev는 서로 다른 호출이다.
프로그램 내부 조건의 모델 응답으로 Runner의 실행 권한이나 대상 경로 검증을 대신하지 않는다.

## 3. 화면 구성

Tkinter 기반의 데스크톱 GUI를 기본안으로 한다. 프롬프트창은 터미널이 아니라
대화 입력줄을 갖춘 채팅 창을 의미한다.

| 영역 | 구성과 동작 |
| --- | --- |
| 상단 | 프로젝트 경로, 프로젝트 선택 버튼, 서비스 이름, 로드 상태, 설정 버튼 |
| 중앙 | 세로 스크롤이 가능한 말풍선 대화. Runner는 왼쪽, 사용자는 오른쪽 |
| 작업 카드 | 선택한 기능, 원본·목적지, DB 표시 이름, 진행률, 결과 경로 |
| 하단 | 여러 줄 입력창, 보내기, 경로 선택, 작업 취소 |

Enter는 보내기, Shift+Enter는 줄바꿈으로 동작한다. 경로 선택 버튼은 현재 수집 중인
경로 입력에 값을 넣으며 자동 실행하지 않는다. 출력이 길면 로그 상세 패널로 펼친다.
UI 스레드에서 네트워크 요청이나 응용 코드를 실행하지 않는다.

초기 안내는 프로젝트 선택 전에도 표시한다. 프로젝트를 선택하지 않고 기능을 물으면
“실행할 Jev 프로젝트를 먼저 선택해 주세요”라고 안내한다. 서비스 변경 시 이전 작업의
입력값을 새 서비스에 재사용하지 않는다. 실행 중에는 서비스 변경을 막고 취소 방법을 표시한다.

## 4. Creator 결과물과 연결

현재 `python_jev_creator`는 Python 조건을 분석·변환하고 `jev_creator_manifest.json`에
선택 위치와 질문을 기록한다. 이 보고서에는 서비스 기능, 호출 진입점, 입력 인자,
부작용 정보가 없으므로 Runner의 실행 명세로 사용할 수 없다.

Runner는 별도의 `jev_service.json`과 명시적인 실행 어댑터를 사용한다.
기존 생성 코드에는 이 두 파일을 추가하는 등록 절차를 제공한다. 파일이 없으면
“이 프로젝트에는 대화 실행 명세가 없습니다”라고 표시하고 등록 화면으로 안내한다.
프로젝트 로드만으로 `main.py`를 실행하거나 Python 모듈을 import하지 않는다.

등록 화면은 AST로 함수 이름·타입 힌트·docstring을 읽어 기능 설명과 인자 매핑의
초안을 제안할 수 있다. 실제 기능 설명, 경로 의미, DB 설정과 실행 방법은 개발자가
확정한다. 코드에서 찾은 함수가 사용자에게 제공할 기능이라고 자동 단정하지 않는다.

향후 Creator가 Runner용 등록 초안을 함께 생성하도록 확장할 수 있다. 기존
Creator 보고서의 의미를 바꾸지 않고 서비스 명세를 별도 파일로 추가한다.

### 서비스 명세 예시

아래 형식은 Runner가 정의할 로컬 규약이며 TypeSafe 공식 API 형식은 아니다.

```json
{
  "schema_version": "1.0",
  "service_id": "photo_archive",
  "name": "사진 보관 서비스",
  "description": "저는 사진을 복사하고, 사진의 메타데이터를 저장합니다.",
  "adapter": "runner_adapter.py",
  "actions": [
    {
      "id": "archive_photos",
      "description": "사진을 복사하고 사진별 메타데이터를 DB에 저장합니다.",
      "input_help": "경로 알려주면, 사진을 복사하고 DB로 해당 metadata 를 저장하겠습니다.",
      "parameters": {
        "source_path": {
          "type": "path",
          "required": true,
          "description": "처리할 사진 파일 또는 폴더",
          "prompt": "처리할 사진 경로를 알려주세요.",
          "must_exist": true
        },
        "destination_path": {
          "type": "directory",
          "required": true,
          "description": "복사한 사진을 보관할 폴더",
          "prompt": "사진을 복사할 폴더를 알려주세요."
        }
      },
      "settings_required": ["metadata_db"],
      "effects": ["copy_files", "write_database"],
      "result_fields": ["copied_count", "metadata_count", "failed_count"]
    }
  ]
}
```

프로젝트별 설정에 `destination_path` 기본값과 `metadata_db` 연결 참조를 저장할 수 있다.
비밀값은 서비스 명세에 넣지 않는다. `service_id`, action ID 중복, 미지원 버전,
누락된 필수 필드와 프로젝트 밖을 가리키는 어댑터 경로는 로드 단계에서 거부한다.

## 5. 대화 해석과 상태 관리

### 의도 선택

Jev Choice에 고정된 대화 의도와 등록된 action ID를 후보로 준다.
`describe_capabilities`, `explain_input`, `provide_input`, `request_execution`,
`cancel`, `status`, `unknown`을 기본 의도로 사용하고, 기능 선택은 별도 Choice로
분리한다. 같은 state에 대해 질문을 독립적으로 판단하므로 기능 선택 결과를
의도 질문의 선행 답변처럼 가정하지 않는다.

state에는 현재 사용자 발화, 최근 필요한 대화, 현재 기능 설명과 수집 단계만
포함한다. 전체 Python 코드, 사진 원본, DB 비밀값은 라우팅 요청에 넣지 않는다.
정확한 경로 문자열은 로컬에서 추출하고 API 전송용 발화에서는 경로를 자리표시자로 바꾼다.

Choice의 선택 확률과 confidence를 각각 검증한다. 초기 기본안은 선택 확률과
confidence가 모두 0.8 이상이며 차순위와 확률 차이가 0.15 이상인 경우에만
자동 전이를 허용한다. 수치는 제품 평가로 조정할 설정값이며 정확도 보장이 아니다.
응답 누락·범위 오류·낮은 확신은 기능 선택 버튼이나 추가 질문으로 연결한다.

### 입력값 수집

Jev에 임의의 파일 경로를 생성하도록 요청하지 않는다. 경로는 경로 선택기 또는
사용자가 직접 입력한 원문에서 추출한다. 경로만 있는 입력은 문자열 전체를 값으로
보존하고, 문장 속 경로는 따옴표 구간 또는 명시적인 경로 접두사로 추출한다.
여러 경로가 감지되면 원본과 목적지를 질문하여 구분한다. 공백·한글·UNC 경로를
처리하고 `eval`이나 쉘 해석으로 값을 평가하지 않는다.

“제가 그러면 … 알려주면 돼?”는 입력 방법 질문으로 처리한다. “그걸로 해 줘”는
현재 기능과 계획을 가리키며, 현재 기능이 없으면 무엇을 실행할지 다시 묻는다.
필수값이 빠졌으면 다음 누락값 하나를 질문한다. 대화 중 원본이나 목적지를
수정하면 실행 계획 버전을 올리고 이전 실행 요청과 분리한다.

### 상태 전이

| 상태 | 대표 입력 또는 사건 | 다음 처리 |
| --- | --- | --- |
| NO_SERVICE | 프로젝트 선택 | 명세 검증 후 IDLE |
| IDLE | 기능 질문 | 기능 설명 후 IDLE |
| IDLE | 특정 기능 요청 | 기능 선택 후 COLLECTING_INPUT |
| COLLECTING_INPUT | 입력 방법 질문 | 필요한 값 설명, 상태 유지 |
| COLLECTING_INPUT | 경로 입력 | 값 검증, 누락값 있으면 질문 |
| COLLECTING_INPUT | 필수값 준비 완료 | 계획 작성 후 READY |
| READY | 명시적 실행 요청 | 현재 계획 버전으로 RUNNING |
| READY | 값 수정 | 계획 갱신 또는 COLLECTING_INPUT |
| RUNNING | 진행 이벤트 | 말풍선 또는 작업 카드 갱신 |
| RUNNING | 완료·실패·취소 완료 | SUCCEEDED / FAILED / CANCELLED |
| 종료 상태 | 새 작업 요청 | 이전 작업과 별개 ID로 새 계획 작성 |

세션에는 `session_id`, 서비스와 버전, 현재 action, 수집값과 출처, 계획 버전,
실행 요청 여부, `job_id`와 상태를 보관한다. 기능 안내나 입력 설명 질문은
현재 작업과 수집값을 지우지 않는다. 실행 중의 “진행 상황은?”은 새 실행으로 처리하지 않는다.

## 6. 실행 계획과 응용 어댑터

실행 계획에는 `plan_id`, `plan_version`, `service_id`, action, 검증한 인자,
설정 참조, 예상 변경 사항을 포함한다. 실행 시 `job_id`를 발급하고 해당 계획의
스냅샷을 고정한다. 전송 버튼 연타로 같은 계획이 중복 실행되지 않게 한다.

응용 어댑터는 다음과 같은 업무 인터페이스를 구현한다.

```python
def execute(action_id, parameters, context):
    # context: job_id, progress(event), is_cancelled(), settings
    # 등록된 action에 대응하는 실제 응용 함수를 호출한다.
    # JSON으로 표현 가능한 결과를 반환한다.
    ...
```

기존 프로그램이 CLI만 제공한다면 등록 시 정해진 인자 매핑을 가진 CLI 어댑터를
만든다. GUI 입력이나 모델 응답으로 임의의 Python 구문, 함수 이름, 쉘 명령을 생성하지 않는다.

Runner worker를 별도 프로세스로 실행하고 worker가 등록된 어댑터를 로드한다.
Python 실행 파일은 프로젝트 설정에서 명시한 인터프리터를 사용한다. 실행은
인자 배열과 `shell=False`로 요청하고 프로젝트 폴더를 작업 디렉터리로 지정한다.
환경은 필요한 설정과 API 키만 전달하며 비밀값을 명령행 인자에 넣지 않는다.
명세를 선택했다고 누락된 패키지를 자동 설치하지 않는다. 필요한 환경을 오류 메시지로 안내한다.

별도 프로세스는 GUI 응답성과 실패 분리를 위한 것이며 임의 Python 코드에 대한
보안 샌드박스는 아니다. 사용자가 실행 대상으로 등록한 로컬 프로젝트를 전제로 한다.

### 작업 이벤트 규약

worker의 표준 출력은 한 줄당 JSON 객체인 JSON Lines로 통일한다. 업무 코드의
일반 print와 로그는 표준 오류로 분리한다. 모든 이벤트에 job ID를 포함한다.

```json
{"type":"progress","job_id":"job-001","completed":5,"total":12,"message":"사진 처리 중"}
{"type":"result","job_id":"job-001","copied_count":12,"metadata_count":12,"failed_count":0}
```

시작·진행·결과·오류·취소 확인을 구분한다. 프로세스 종료 코드가 0이더라도 결과
이벤트가 없으면 정상 완료로 표시하지 않는다. 결과 이벤트와 종료 코드가 모두
정상일 때 완료 문장을 만든다. stdout/stderr의 원문은 명령이나 대화 지시로 해석하지 않는다.

## 7. 사진 서비스 실행 예시

사진 서비스는 Runner의 기본 내장 기능이 아니라 연결할 응용 서비스의 기준 예제다.
실제 사진 복사와 메타데이터 저장 함수가 있어야 해당 기능을 안내한다.

1. 원본 경로 존재 여부, 읽기 권한, 목적지 쓰기 가능 여부를 검증한다.
2. 대상 확장자와 하위 폴더 포함 여부를 서비스 설정에 따라 결정한다.
3. 파일 목록을 계획에 고정하고 복사 직전 변경·삭제 여부를 다시 확인한다.
4. 사진을 목적지에 복사하고 원본은 유지한다. 동명 파일은 덮어쓰지 않고 중복 정책을 적용한다.
5. 파일명, 원본·복사 경로, 크기, 촬영 시각 등 지원하는 메타데이터를 추출한다.
6. 사진별 DB 트랜잭션으로 저장하고 작업 상태를 기록한다.
7. 성공·건너뜀·실패 건수를 나누어 결과로 반환한다.

DB 접속·테이블 준비 상태는 복사 전에 점검한다. EXIF가 없으면 가능한 파일 정보만
저장하고 촬영 시각은 빈값으로 처리한다. 파일 복사와 DB 저장을 하나의 원자적
트랜잭션이라고 가정하지 않는다. 복사 후 DB 저장에 실패한 파일은 부분 실패로
기록하여 재시도 시 DB 저장 단계부터 복구할 수 있게 한다.

DB에는 작업 ID, 원본 상대 경로와 내용 해시 기반의 중복 식별자를 사용한다.
중단 후 재시작 시 기존 작업 상태와 실제 복사 파일을 확인한 뒤 재시도 범위를
정한다. “실패한 것만 다시 해 줘”는 이전 작업의 실패 항목으로 새 계획을 생성한다.

## 8. 오류와 취소 처리

| 상황 | 대화 및 처리 |
| --- | --- |
| Jev 키 없음 또는 API 연결 실패 | 기능 목록과 입력 안내는 계속 제공하고, 기능 버튼과 명시적 실행 버튼으로 진행 |
| 지원하지 않는 요청 | 등록된 기능 범위를 설명하고 가능한 기능 제시 |
| 모호한 의도 또는 낮은 확신 | 기능·실행 여부를 다시 질문. 모델 추측으로 실행하지 않음 |
| 없는 경로·권한 오류 | 잘못된 필드를 표시하고 재입력 요청, 다른 수집값 유지 |
| DB 미설정 | 설정 화면 안내, 작업 시작 전 해결 |
| 업무 코드 예외·비정상 종료 | 실패 단계와 실제 부분 결과 표시 |
| 실행 중 취소 | 취소 토큰 전달, 안전한 파일·DB 작업 경계에서 종료 |
| 취소에 응답하지 않는 작업 | 강제 종료 선택 제공, 이미 완료한 변경과 미확인 상태 구분 |
| 창 닫기 중 작업 실행 | 계속 실행 여부 또는 취소 후 종료 선택 제공 |

취소는 이미 복사한 파일이나 저장한 DB 데이터를 자동 삭제하는 의미가 아니다.
실패를 완료로 바꾸거나 확인되지 않은 처리 건수를 추정하지 않는다.

## 9. 설정과 저장 데이터

서비스 설정에는 인터프리터, 프로젝트 경로, 복사 목적지, DB 연결 참조를 저장한다.
Jev 설정은 `TYPESAFE_API_KEY` 환경 변수, 모델 별칭, 요청 타임아웃과 판단 기준값으로 구성한다.
Runner 라우팅과 응용 내부 Jev를 각각 사용할지 설정하고 UI에서 상태를 구분한다.

대화는 기본적으로 세션 메모리에만 유지한다. 작업 재개에 필요한 실행 계획과
결과는 로컬 SQLite 작업 이력에 저장한다. 대화 내보내기는 사용자가 요청할 때
수행하며, API 키와 DB 접속 비밀값을 기록하지 않는다. 경로·EXIF 등 실제 개인 데이터는
로그 상세 수준에 따라 저장 범위를 제한한다.

첫 Jev 사용 설정에 라우팅 발화가 TypeSafe API로 전송된다는 사실을 표시한다.
응용 내부 Jev가 보내는 변수 값은 Creator의 선택 위치와 별도로 검토한다.

## 10. 구현 파일 구성안

```text
python_jev_runner/
├── README.md                 # 이 설계 문서
├── main.py                   # 예정: GUI 실행 진입점
├── gui.py                    # 예정: 말풍선, 입력창, 작업 카드
├── conversation.py           # 예정: 세션 및 상태 전이
├── intent_router.py          # 예정: Jev 의도·기능 판단
├── response_renderer.py      # 예정: 명세·결과 기반 문장 생성
├── service_registry.py       # 예정: 서비스 명세 로드와 검증
├── parameter_collector.py    # 예정: 경로 추출과 입력 검증
├── execution_manager.py      # 예정: 계획과 프로세스 수명 관리
├── worker.py                 # 예정: 어댑터 실행과 JSONL 이벤트
├── history_store.py          # 예정: 작업 이력과 재시도 정보
├── schemas/                  # 예정: 서비스·계획·이벤트 JSON Schema
├── examples/photo_service/   # 예정: 대화 실행용 사진 서비스 예제
└── tests/                    # 예정: 상태·프로토콜·실행 통합 검증
```

Runner의 네트워크 요청과 이벤트 읽기는 작업 스레드에서 수행하고, GUI 갱신은
큐를 통해 Tk 메인 스레드로 전달한다. 실행 작업은 worker 프로세스에서 수행한다.

## 11. 구현 단계와 완료 기준

### 1단계 서비스 등록과 말풍선 GUI

초기 안내 문구, 프로젝트 선택, 명세 검증, 기능 안내와 경로 입력을 구현한다.
Jev 없이도 기능 버튼과 명세 기반 응답으로 기본 흐름을 검증한다.

### 2단계 Jev 대화 해석

의도·기능 선택, 대화 문맥 유지, 모호한 질문 재확인, 입력값 수정과 실행 계획을 구현한다.
대표 한국어 발화와 말바꾸기 사례로 평가하고, 임계값은 평가 결과에 맞춰 조정한다.

### 3단계 실제 응용 실행

worker와 어댑터, 사진 예제, 진행률, 취소, 부분 실패와 재시도를 연결한다.
Creator 생성 프로젝트에 명세·어댑터를 추가한 뒤 대화로 실행되는지 통합 검증한다.

| 인수 검증 | 기대 결과 |
| --- | --- |
| 앱 시작 | 첫 말풍선이 “저는 jev 코드를 실행하는 runner 입니다”와 일치 |
| 기능 질문 | 등록된 서비스 기능만 설명 |
| “경로 알려주면 돼?” | 실행하지 않고 입력 방법 설명 |
| 후속 경로 입력 | 앞선 기능과 연결, 부족한 목적지나 DB 설정은 추가 요청 |
| 명시적 실행 요청 | 검증된 현재 계획으로 한 번 실행 |
| 계획 수정 후 실행 | 수정된 경로를 사용하고 이전 계획을 실행하지 않음 |
| 모호한 의도·서비스 변경 | 추가 질문 또는 문맥 초기화, 잘못된 기능 실행 없음 |
| 공백·한글 경로 | 원문 경로를 유지하여 처리 |
| 정상 사진 처리 | 원본 보존, 복사 파일·DB 행과 완료 보고의 건수 일치 |
| API·DB·파일 오류 | 멈추지 않는 GUI, 실패·부분 성공 상태 정확히 표시 |
| 취소·중복 클릭·재시도 | 완료한 부작용 표시, 작업 중복 실행 방지 |
| 명세 없는 기존 Creator 결과 | 자동 실행 없이 등록 절차 안내 |

자동 검증은 모의 Jev 응답으로 상태 전이를 재현하고, 임시 사진 폴더와 SQLite로
실제 복사·저장을 검증한다. 별도의 API 키가 있는 환경에서 공식 Jev 온라인 연동을
검증한다. GUI는 말풍선 정렬, 스크롤, 한글 줄바꿈, 실행 중 응답성을 직접 확인한다.
