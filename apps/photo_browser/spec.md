# Photo Browser 구조 및 확장 명세

작성 기준: 2026-10-22의 `apps/photo_browser` 소스 코드. 아래 1~8번은 현재 구현이며, 9~10번은 아직 구현하지 않은 확장 제안이다. 설치·운영 명령과 상세 설정은 [README.md](README.md)를 참고한다.

이 앱은 여러 위치의 사진·동영상을 스캔해 JSON 카탈로그로 관리하고, 원본을 보존하면서 분류별 관리 디렉토리로 통합 복사하는 도구다. **스캔은 등록, 병합은 실제 복사, 비교는 복사 결과 검증**으로 역할이 나뉜다.

```text
로컬 / WebDAV / HTTP manifest
              │
              ▼
설정 → 목록 집계 → 메타데이터·해시 분석 → JSON 카탈로그
                                           │
                       ┌───────────────────┼───────────────────┐
                       ▼                   ▼                   ▼
                  검색·분류 편집      병합 미리보기         중복 판별
                                           │
                                           ▼
                                  공간 검사 → 검증 복사
                                           │
                                  관리 디렉토리 + 보고서
                                           │
                                 원본 대조 / 휴지통·복원

접근 경로: 웹 UI → Flask API → Library / ScanEngine
          CLI ─────────────→ Library / 복사 비교
```

## 1. 실행 구조와 웹·CLI 인터페이스

**관련 코드:** [app.py](app.py), [library_api.py](library_api.py), [cli.py](cli.py), [templates/index.html](templates/index.html), `static/`

`app.py`가 Flask 앱을 구성하고 폴더 탐색·미디어 제공·서버 정보 API를 담당한다. `library_api.py`는 라이브러리 작업을 API로 노출하며, 핵심 처리는 `Library`에 위임한다. 화면은 서버 템플릿과 JavaScript로 구성된다.

CLI는 HTTP 서버를 거치지 않고 같은 DB와 처리 코드를 사용한다. `config`, `status`, `merge`, `compare`, `backup`, `backup-check`, `restore`와 분석 Skill 목록·등록·요청 준비·결과 저장 명령을 제공하며 JSON을 출력한다. 현재 CLI에는 스캔 실행 명령이 없으므로 스캔 실행·재개는 웹/API에서 수행한다.

웹서버 실행 중에도 CLI를 사용할 수 있다. 다만 서버와 같은 `--db`, `--root`를 지정해야 하며, 병합·비교 등 잠금을 요구하는 작업은 다른 DB 쓰기 작업과 동시에 실행할 수 없다.

## 2. 경로 설정과 다중 소스 수집

**관련 코드:** `Library.config()`, `save_config()`, `local()`, `remote_files()`, `materialize()` — [library.py](library.py)

| 경로·설정 | 역할 |
| --- | --- |
| 허용 루트 `--root` | 로컬 파일 접근을 허용하는 경계 |
| 소스 `sources[].root` | 원본 디렉토리 또는 원격 URL |
| 관리 루트 `managed_root` | 통합 복사본과 휴지통 저장 위치 |
| DB `--db` | 설정·카탈로그·체크포인트·보고서 저장 위치 |

소스마다 ID, 프로토콜, 카테고리, 소유자, 재귀 탐색 여부 등을 지정한다. 로컬 파일 외에 WebDAV와 HTTP를 지원한다. WebDAV는 디렉토리를 순회하고, HTTP는 `manifest.json` 목록을 읽는다. 일반 웹페이지의 HTML 디렉토리 목록을 해석하는 방식은 아니다.

원격 파일은 임시 로컬 파일로 내려받아 분석·복사한다. 인증 정보는 `credential_ref`에 대응하는 환경변수에서 읽으며 JSON에 비밀번호를 저장하지 않는다. 로컬 경로는 정규화 후 허용 루트 내부인지 검사하고, 관리 디렉토리와 DB는 원본 스캔 대상에서 제외한다.

## 3. 스캔 엔진과 중단·복구

**관련 코드:** [scan_engine.py](scan_engine.py), `Library.scan()`

스캔은 **목록 집계 → 파일 분석 → 카탈로그 발행** 순서로 진행된다. 목록 집계가 끝나야 정확한 전체 파일 수와 처리 백분율을 계산할 수 있다.

| 실행 모드 | 처리 방식 |
| --- | --- |
| `incremental` | 로컬 파일의 크기·수정 시각이 같으면 기존 분석 결과 재사용 |
| `restart` | 새 세션으로 목록·메타데이터·해시를 전체 재분석 |
| `resume` | 저장된 목록과 결과 저널을 읽고 미처리 항목부터 재개 |

세션별 `inventory.jsonl`, `results.jsonl`, `state.json`을 저장한다. 마지막 JSONL 레코드가 비정상 종료로 잘린 경우 복구하며, 목록 집계 중 중지했다면 재탐색하면서 중복 경로를 제외한다. 소스 설정이 달라진 세션은 그대로 이어하지 못하도록 검사한다.

디스크 여유 공간과 중지 요청을 확인하고, 원격 다운로드·해시 처리에서도 중지에 응답한다. 완료 부분을 발행할 공간이 없으면 저널을 유지하고 공간 확보 후 재개할 수 있다. 재스캔 시 사용자가 편집한 분류·이벤트·태그와 삭제 상태를 보존한다.

스캔의 `completed`만으로 모든 파일이 성공했다고 판단하지 않는다. 파일별 `errors`, 카탈로그 `published`, 처리 수를 함께 확인해야 한다.

## 4. JSON 카탈로그와 메타데이터 모델

**관련 코드:** `metadata()`, `Library.commit()`, `items()`, `item()`, `facets()` — [library.py](library.py)

미디어 항목은 다음 정보를 가진다.

| 정보 묶음 | 주요 필드와 의미 |
| --- | --- |
| 식별·무결성 | `media_id`, 원래 파일명, 종류, 크기, SHA-256, 수정 시각 |
| 촬영 정보 | `capture`: 촬영 시각, 날짜 기준, GPS, 해상도, 영상 길이, 추출 오류 |
| 사용자 분류 | `classification`: 카테고리, 소유자, 사람 ID, 이벤트 이름, 태그 |
| 물리적 위치 | `locations`: 원본·관리 복사본, 프로토콜, 경로·URI, 위치 상태 |
| 수명·검증 | `lifecycle`, `revision`, 검증 결과 |

사진은 Pillow로 EXIF를, 영상은 `ffprobe`로 메타데이터를 읽는다. 촬영일이 없으면 사용 가능한 실제 생성일·수정일을 사용하며, 원격 파일은 서버 수정일을 활용한다. 날짜 근거를 저장하고, EXIF에 시간대가 없으면 알 수 없는 상태로 남긴다. Linux ctime을 촬영일이나 생성일로 간주하지 않는다.

카탈로그는 `media/<카테고리>/<소유자>/<연>/<월>/` 아래 최대 100개 항목씩 나눈 JSON 청크로 저장한다. 새 세대 청크를 모두 기록한 뒤 `index.json`을 원자적으로 교체하므로 읽는 쪽이 미완성 세대를 참조하지 않도록 구성되어 있다. **현재 데이터의 기준은 `index.json`이며, 과거 청크까지 모두 합산하면 안 된다.**

개별 항목 조회는 ID→청크 조회 캐시를, 필터 후보 목록은 인덱스 요약·캐시를 사용한다. 다만 전체 편집·병합 등은 여전히 여러 항목을 메모리로 읽고 세대를 다시 발행한다. 이전 세대 자동 정리는 구현되어 있지 않다.

## 5. 검색·분류 편집과 중복 관리

**관련 코드:** `Library.edit()`, `apply_source_classification()`, `duplicates()`, `duplicate_sources()`, `unregister_duplicate_source()`, [library_api.py](library_api.py), [static/library.js](static/library.js)

라이브러리는 날짜 범위, 기준 날짜 주변, 사진·영상 종류, 카테고리, 소유자, 사람, 이벤트, 태그와 텍스트 검색을 지원한다. 결과는 페이지 단위로 제공한다. 선택 항목의 분류 정보를 일괄 변경하고, 기존 항목에 소스의 카테고리·소유자를 적용할 수 있다. 분류 변경이 기존 관리 파일을 자동으로 이동시키지는 않는다.

중복은 세 가지 관점으로 구분한다.

- **내용 중복:** SHA-256이 같은 활성 미디어 항목을 그룹화한다.
- **촬영 조건 후보:** 촬영 시각과 반올림한 GPS 좌표가 같은 항목을 후보로 표시한다. 시각적 동일성을 확정하지 않는다.
- **소스 중복:** 스캔된 상대 경로·크기 목록으로 소스 후보를 찾고, 마지막 스캔 해시의 일치 여부도 제공한다. 실제 디스크를 다시 검사하는 기능은 아니다.

중복 소스 정리는 지정한 소스 등록과 그 소스 전용 관리 복사본을 정리한다. 원본과 다른 항목이 참조하는 공유 파일은 보존하며, 변경 전 항목과 삭제 내역을 `source_cleanup/`에 남긴다. **이 정리의 전용 관리 파일 삭제는 일반 휴지통 이동과 달리 영구 삭제다.**

## 6. 통합 병합 복사와 파일 보호

**관련 코드:** `Library.merge()`, `_merge()`, `resolve_merge_target()`, `merge_space()`, `publish_merge_copy()`

병합은 원본을 유지한 채 활성 항목을 다음 경로로 복사한다.

```text
managed_root/<category_id>/<owner_id>/<year>/<month>/<원래 파일명>
```

현재 구현은 원래 파일명을 기본으로 사용한다. 같은 출력 경로에 동일 내용이 있으면 재사용하고, 내용이 다르면 `_중복`, `_중복_2` 등의 이름으로 보존한다. 서로 다른 폴더의 동일 내용 파일을 전역적으로 한 파일로 통합하는 방식은 아니다.

미리보기와 실제 실행은 같은 이름 선택 규칙을 사용하지만, 실행 시점의 파일 상태에 따라 경로가 달라질 수 있다. 실행 전에는 신규 복사량, DB 증가 예상량, 최소 여유 공간, 원격 임시 공간을 검사한다. 부족하면 `blocked_low_space`로 종료한다. 공간 검사는 예약 기능이 아니므로 다른 프로그램의 디스크 사용까지 보장하지 않는다.

실제 복사는 임시 파일에 수행하고 SHA-256을 확인한 뒤 대상 경로에 게시한다. 대상이 도중에 생긴 경우 다시 비교해 재사용하거나 이름을 바꾸며 기존 파일을 덮어쓰지 않는다. 관리 위치는 항목의 `locations`에 추가하고, `merges/<merge_id>.json`에 처리 내역을 저장해 중지·이어하기를 지원한다.

## 7. 복사 검증·실행 보고서·휴지통

**관련 코드:** [copy_check.py](copy_check.py), [merge_history.py](merge_history.py), `Library.verify()`, `trash()`, `restore()`, `purge()`

검증과 보고서는 목적·범위가 다르다.

| 기능 | 확인하는 내용 |
| --- | --- |
| CLI `compare` | 소스를 다시 탐색해 파일 수·바이트 집계, 미스캔·누락·원본 변경·복사본 불일치 검사 |
| CLI `compare --quick` | 크기 중심 비교. 같은 크기의 내용 손상은 검출하지 못함 |
| API 정밀 확인 `verify` | 선택 항목의 위치별 존재·크기 및 선택적으로 해시 검사 후 DB에 검증 결과 저장 |
| 병합 실행 보고서 | 실행별 처리 수·시간·오류·이름 변경·관리 디렉토리 전후 변화 기록 |

`compare`는 기본적으로 원본과 등록된 관리 복사본의 SHA-256을 스캔 당시 값과 대조한다. 중복 원본이 하나의 복사본을 공유할 수 있으므로 파일 수의 일치만으로 성공을 판정하지 않는다. 비교 집계는 지원 미디어를 대상으로 하며, 관리 디렉토리의 추가 파일을 모두 복사 오류로 간주하지는 않는다.

병합 실행마다 `reports/merges/`에 JSON·독립 HTML 보고서를 저장한다. 중지와 이어하기는 서로 다른 `report_id`를 가지며 같은 `merge_id`로 연결된다. 전후 집계는 일반 파일도 포함한 경로·크기·수정 시각 조사로, 전체 파일 내용의 해시 검증과는 다르다. 보고서의 논리적 바이트 합계와 디스크 실제 할당 용량도 구분해야 한다.

일반 삭제는 관리 복사본을 `.trash`로 이동하고 복원 기록을 남긴다. 원본은 삭제하지 않는다. 공유 관리 파일은 참조를 확인하고, 복원 시 기존 파일을 덮어쓰지 않는다. 영구 삭제는 일회용 확인 절차를 거치며 자동 삭제하지 않는다.

[backup.py](backup.py)는 DB와 관리 디렉토리 전체를 파일별 SHA-256 목록과 함께 새 폴더에 백업한다. `backup-check`로 파일 목록·내용을 재검증하고, `restore`는 새 폴더에 복원하며 DB의 관리 파일·URI·휴지통·작업 기록 경로를 새 위치로 갱신한다. 사진 내용·촬영 메타데이터·태그를 유지하고 파일 수정 시각을 복사한다. 원본 소스는 포함하지 않으며 미병합 활성 항목 수를 알린다. 기존 라이브러리를 덮어쓰지 않고 과거 HTML 보고서는 원래 기록으로 보존한다.

## 8. 작업 운영·동시 실행·주변 기능

**관련 코드:** [library_api.py](library_api.py), `Library.writing()`, [directory_history.py](directory_history.py), [server_network.py](server_network.py)

웹의 긴 작업은 단일 백그라운드 워커에서 실행하고 `jobs/`에 상태를 저장한다. 화면을 새로고침해도 상태를 조회할 수 있으며, 서버 재시작 시 실행 중이던 기록은 `interrupted`로 처리한다. 손상된 작업 기록은 백업하고 오류 상태로 전환한다. 상태 기록만으로 사진 복사 성공을 추정하지 않는다.

DB 변경에는 프로세스 내부 잠금과 운영체제 파일 잠금을 사용한다. 서버와 CLI의 동시 쓰기를 막지만 외부 프로그램이 원본·관리 파일을 바꾸는 것까지 제어하지는 않는다. 운영은 서버 프로세스 하나를 전제로 한다.

`PHOTO_BROWSER_PASSWORD`를 설정하면 웹 페이지·API에 Basic 인증을 적용한다. 변경 요청은 전용 헤더와 Origin을 검사한다. 현재 사용자별 권한 모델은 없으며 `owner_id`는 사진 분류 값이다.

기존 폴더 탐색은 카탈로그 등록 없이 사진을 볼 수 있고, 탐색량 제한·추가 불러오기·경로 히스토리를 제공한다. 서버 주소 정보는 별도 스레드로 갱신하며 공인 IP 확인에 외부 서비스를 사용한다. 이 조회의 실패가 스캔 처리를 중단시키지는 않는다.

검증 코드는 `test_app.py`, `test_library.py`, `test_scan_engine.py`, `test_cli.py` 및 디렉토리 히스토리·병합 보고서·네트워크 테스트로 나뉜다. 원본·관리 파일·JSON DB·실행 보고서는 함께 백업할 운영 대상으로 본다.

## 10. 향후 제안: 메타데이터 관리 기능

분석 기반 레이어로 [analysis_skills.py](analysis_skills.py)를 구현했다. 일반 사진·명함·견적서·일반 문서의 기본 페르소나, 사용자 페르소나 버전 관리, 유형별 출력 JSON 규격, 웹·CLI 프롬프트 준비 및 응답 검증·별도 저장을 제공한다. 사진 내용·촬영 시각·태그를 유지하고 `db/ai`에 스냅샷과 분석 결과를 보관한다. 현재 실제 모델 서버 호출·인증·검색 인덱스 연결은 구현하지 않았으며 아래 장기 기능과 구분한다.

**아래 내용은 향후 개발 요구사항이다.** 현재도 이벤트·태그·사람 ID 편집과 필터 검색은 가능하지만, 다음은 관리 파일 중심 편집, 사람 표시 이름·장소 통합 검색, LLM 설명·의미 검색까지 확장하기 위한 요구사항이다. 먼저 시간 정보와 사용자 입력을 보존하는 편집·검색을 구현하고 장기적으로 자동 분석을 연결한다.

### 관리 파일 태그 편집과 시간 보존 규칙

사용 흐름은 **관리 사진 선택 → 이벤트·사람·장소 입력 → 변경 미리보기 → 저장 → 전체 검색에서 확인**으로 한다. 일괄 편집은 추가·교체·제거를 구분하고, 기본 추가 동작은 기존 태그를 보존한다. 사람은 표시 이름으로 선택하되 내부 ID로 연결하고, 장소는 사용자가 입력한 이름과 GPS·주소 정보를 분리해 저장한다. GPS가 없는 사진에도 장소 이름을 붙여 검색할 수 있어야 한다.

태그는 논리적 사진 항목에 연결해 원본·관리 복사본 어느 위치로 열어도 동일하게 조회한다. 여러 항목이 동일 관리 파일을 공유할 때에는 편집 적용 범위를 알리고, 공유 항목 전체에 적용할지 사용자가 선택하게 한다. 원본이 오프라인이어도 관리 복사본의 태그 편집과 검색은 가능해야 한다.

일반 태그 편집에서는 `capture.captured_at`, `date_key`, 시간대, 날짜 근거와 파일 수정 시각을 변경하지 않고, 물리적 파일의 이동·이름 변경·EXIF 재기록도 하지 않는다. 편집 시각은 별도의 메타데이터 갱신 시각으로 저장한다. 파일을 쓰지 않으므로 생성 시각도 변경을 유발하지 않는다. 파일 접근 시각은 읽기 동작과 운영체제 설정에 따라 달라질 수 있어 보존 판정에서 제외한다. 날짜·시간대 보정은 사용자가 명시적으로 실행하는 별도 작업으로 한정한다.

XMP 내보내기를 지원할 경우에도 별도 sidecar 파일에 기록한다. 재스캔·재병합·백업 복원 후 태그가 유지되고, 편집 전후 사진 파일의 SHA-256과 수정 시각 및 촬영 정보가 동일한지 검증한다.

### 장기 개발: 사진 설명과 지능형 검색

분석은 백그라운드 작업으로 실행하고 중지·이어하기·실패 재시도·진행률을 제공한다. 파일 해시와 모델·프롬프트 버전으로 이미 분석한 사진을 식별해 중복 처리를 줄인다. 로컬 모델과 외부 서비스 사용을 선택할 수 있게 하고, 외부 전송은 사용자가 설정한 범위 내에서 수행한다.

분석 결과는 `ai_annotations` 같은 별도 영역에 설명, 추천 태그, 모델·프롬프트 버전, 분석 시각, 대상 해시, 처리 상태를 기록하는 방안을 제안한다. 사용자 승인·수정 이력도 별도로 보관한다. 사람의 실제 이름과 정확한 장소는 사용자 태그·기존 GPS 등 확인 가능한 근거로 연결하고, 모델이 외형이나 장면만으로 추정한 값을 확정 메타데이터로 기록하지 않는다.

검색은 **정확한 태그·키워드 검색 + 설명 텍스트의 임베딩 기반 의미 검색 + 구조화 필터**를 결합하는 방향을 권장한다. 예를 들어 “제주도 가족여행에서 바닷가를 걷는 사진”은 이벤트·장소 태그와 장면 설명을, “2024년 민수 생일에 케이크가 나온 사진”은 날짜·사람·이벤트 조건과 설명을 함께 사용한다. 자연어에서 해석한 필터는 화면에 표시하고 수정할 수 있게 한다.

임베딩 인덱스에는 사진 ID·대상 해시·설명 버전·임베딩 모델 버전을 연결하고, 태그나 설명 수정 시 갱신하며 삭제·휴지통 항목은 검색 대상에서 제외한다. 인덱스 재생성이 가능하도록 사용자 입력과 AI 설명 원문을 DB에 보존한다. 결과에는 태그 일치·설명 일치 등 검색 근거를 표시하고, 실제로 존재하며 접근 가능한 사진을 연결한다. 의미 유사도는 순위 점수로 사용하며 사실의 확률로 표시하지 않는다.

개발 순서는 **시간 보존형 태그 편집 → 이벤트·사람·위치 통합 검색 → LLM 설명 생성 → 의미 검색 결합**을 권장한다. 각 단계에서 기존 촬영 시간과 사용자 태그 보존을 검증하고, 최종 검색 품질은 사용자가 준비한 대표 질의와 정답 사진 목록으로 평가한다.
