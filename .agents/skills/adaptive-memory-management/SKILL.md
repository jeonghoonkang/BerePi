# 메모리 관리 코드 작성

데이터 규모가 증가해도 전체 정보를 RAM에 누적하지 않도록 하고, 실행 환경의 여유 메모리 변화에 맞춰 캐시를 조절한다. 기존 처리 결과·검증·재시작 의미를 보존한다. 대상 언어와 플랫폼에 맞게 구현하며 아래 수치를 모든 프로젝트의 고정 정책으로 적용하지 않는다.

## 재사용 입력 프롬프트

다음 입력을 사용자 요청 또는 구현 작업의 출발점으로 사용할 수 있다. 미기재 항목은 저장소에서 확인하고, 확인할 수 없는 값은 가정과 제한을 명시한다.

```text
대상 프로젝트/경로: [프로젝트 경로]
대상 명령 또는 처리 구간: [스캔/변환/DB 정리/서버 작업 등]
운영 환경: [운영체제, 물리 RAM, 컨테이너/서비스 제한; 모르면 자동 확인]
데이터 특성: [예상 건수, 파일·레코드 크기, 반복 조회 패턴]
메모리 목표: 기본 자동 계산, 사용자 옵션은 캐시 상한으로만 사용
디스크 작업 공간: [임시 인덱스 허용 위치와 여유 공간; 모르면 기존 정책 확인]
반드시 유지할 동작: [결과 호환성, 안전 검증, 중단·재시작 등]
진행 표시: [기존 로그/상태 API/CLI 화면과 갱신 간격]

가용 메모리와 실행 제한을 자동 감지하고, 바이트 단위 캐시 예산과
메모리 압력에 따른 적응형 축소·확대를 구현해 주세요.
전체 데이터를 RAM에 보관하는 구조는 스트리밍과 디스크 기반 인덱스로 개선하고,
실제 사용량·가용량·캐시 예산·조절 사유를 기존 진행 로그에 표시해 주세요.
낮은 메모리, 지표 확인 실패, 대량 데이터, 중단·재시작을 테스트하고,
캐시 예산과 전체 프로세스 RAM 제한의 차이 및 실측 결과를 설명해 주세요.
커밋·푸시 여부: [요청한 경우에만 수행]
```

## 구조 선택

- 전체 데이터 사전·집합, 정렬할 전체 경로 목록, 제한 없는 검증 캐시, 전체 파일 읽기, 병렬 작업의 복제 버퍼를 먼저 찾는다. 필수 상태와 재계산 가능한 캐시를 구분한다.
- 필수 대용량 상태는 SQLite 인덱스, 외부 정렬, 기존 DB의 조회 기능 등 프로젝트에 맞는 디스크 구조로 옮긴다. SQLite라면 키 인덱스와 제한된 조회를 사용하고 `fetchall()`로 다시 전체를 올리지 않는다. 페이지 캐시·mmap·임시 정렬 메모리도 고려한다.
- 파일·배치·청크 단위로 처리하고 이전 버퍼를 다음 큰 할당 전에 해제한다. `read(최대 허용 크기)`가 작은 파일에서도 큰 임시 할당을 만드는지 확인한다. 실제 크기로 읽는 경우 크기 증가·내용 변경·읽기 한도를 검증한다.
- 임시 인덱스 위치·디스크 부족·잠금·권한·정상 종료 및 강제 종료 후 잔여 파일을 다룬다. 재시작에 필요한 영구 상태와 재생성할 임시 상태를 구분한다. 캐시 퇴출이 결과의 정확성에 영향을 주어서는 안 된다.

## 자동 예산과 제어

- 총 물리 RAM이 아니라 현재 가용 메모리를 출발점으로 사용한다. Linux에서는 `MemAvailable`, cgroup v1/v2의 사용량과 제한, 확인 가능한 상위 cgroup의 제약, 필요하면 주소 공간 제한을 함께 적용한다. cgroup 경로는 mount root와 namespace를 고려해 해석한다. 다른 플랫폼에서는 해당 OS 지표를 사용하고 감지하지 못하는 제한을 명시한다.
- 초기 예산은 필수 상태·동시 작업 버퍼·안전 여유를 고려해 보수적으로 정한다. 사용자 옵션은 자동 안전 범위를 낮출 수 있는 상한이며 즉시 선할당하지 않는다. 지표가 없으면 작은 고정 예산 또는 캐시 비활성화를 선택하고 자동 확대하지 않는다.
- 캐시는 개수보다 바이트로 제한한다. 문자열·중첩 객체·키·캐시 관리 비용을 포함하고, 항목이 예산보다 크면 캐싱하지 않는다. 여러 캐시가 각각 전체 예산을 소비하지 않도록 공유 예산 또는 명시적인 분할을 사용한다.
- 시간 기반 피드백 제어를 둔다. 안정적인 기간이 유지되면 조금씩 확대하고, 여유 감소·메모리 압력·스왑 지연이 나타나면 빠르게 축소한다. AIMD, 서로 다른 확대·축소 임계값, 재확대 대기 시간을 조합할 수 있다. 측정 주기와 임계값은 데이터·OS에 맞춰 선택하고 테스트에서 주입 가능하게 한다.
- RAM 부족 시 새 캐시 저장 중단, LRU 퇴출, 배치·동시성 감소를 적용한다. 진행할 최소 작업 메모리도 없으면 체크포인트를 보존하고 중단 또는 일시 중지한다. OOM 강제 종료를 정상적인 흐름으로 사용하지 않는다.
- 캐시 퇴출 후 RSS가 즉시 줄어든다고 가정하지 않는다. 파서·네이티브 라이브러리·할당기·SQLite·파일 캐시의 비용을 구분한다. RSS와 컨테이너 전체 사용량은 서로 다른 범위다. 캐시 상한을 전체 프로세스 RAM의 강제 한도로 설명하지 않는다.

## 관측과 검증

- 기존 진행 로그에 현재 RSS, 시스템 가용 메모리, 유효 실행 제한, 지표 출처, 캐시 예산·사용량·히트·미스·퇴출, 조절 사유, 메모리 압력을 추가한다. 알 수 없는 값은 0으로 위장하지 않는다.
- 긴 I/O 중에도 기존 heartbeat에서 관측할 수 있게 한다. 측정 비용과 스레드 안전성을 고려하며, 작업 스레드 전용 DB 연결을 heartbeat에서 사용하지 않는다. 기존 로그 순환과 stdout JSON 등 출력 계약을 보존한다.
- 주입 가능한 지표·시계로 부족한 메모리, 과도한 사용자 상한, 지표 실패, 컨테이너 상위 제한, 빠른 축소, 안정 후 확대, 진동 방지, 큰 캐시 항목을 검증한다.
- 캐시를 비우거나 매우 낮은 예산으로도 결과와 안전 검증이 동일해야 한다. 중단 후 재시작, 디스크 부족, 변경된 입력 처리의 핵심 경로를 검증한다.
- 합성 대량 데이터를 만들어 전체 자료를 RAM에 유지하지 않는지 측정한다. 유지 메모리와 최고 사용량을 구분하고 파이썬 heap 측정만으로 네이티브·프로세스 RSS까지 검증했다고 주장하지 않는다. 운영 데이터로 OOM을 유발하는 테스트를 하지 않는다.
- 관련 회귀 테스트를 실행하고 실제 OS/컨테이너에서 확인한 범위와 모의 지표로만 검증한 범위를 구분해 보고한다. 문서에는 자동 정책, 선택 상한, 임시 디스크 사용, 로그 확인, 중단 후 재시작 방법과 남은 제한을 남긴다.
